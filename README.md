# VPNSOPR v0.6.0

Independent multi-node reverse TCP tunnel manager written in Go.

## Build
```bash
go build -o vpsopr-server ./cmd/server
go build -o vpsopr-client ./cmd/client
```

## Gateway VPS
Create a TLS certificate whose SAN matches the DNS name used by agents:
```bash
openssl req -x509 -newkey rsa:3072 -keyout server.key -out server.crt -days 365 -nodes -subj "/CN=tunnel.example.com" -addext "subjectAltName=DNS:tunnel.example.com"
```
Start the gateway:
```bash
./vpsopr-server -listen 0.0.0.0:8443 -cert server.crt -key server.key \
  -panel 127.0.0.1:7777 -panel-token "REPLACE-WITH-32-CHAR-RANDOM-PANEL-SECRET"
```

## Panel access
```bash
ssh -L 7777:127.0.0.1:7777 root@GATEWAY_IP
```
Open `http://127.0.0.1:7777`, authenticate with the panel token, and register each remote VPS. The panel displays a node ID and one-time agent token; copy the token immediately.

## Remote VPS agent
```bash
./vpsopr-client -server GATEWAY_IP:8443 -server-name tunnel.example.com \
  -ca server.crt -node-id NODE_ID -token ONE_TIME_NODE_TOKEN -target 127.0.0.1:3000
```
Create a port forward in the panel, selecting that node ID. Example: gateway listen `0.0.0.0:443`, remote target `127.0.0.1:443`.

## Included
- Multi-VPS node registry with per-node random credentials (stored as SHA-256 hashes)
- TLS 1.3 agent connections and reconnect loop
- Multiple TCP port forwards routed to selected nodes
- Web panel node registration, online/offline status, tunnel create/delete
- Persistent node and forward configuration
- Token-authenticated management APIs

## Security notes
Keep the panel on localhost and access it through SSH forwarding or a secured HTTPS reverse proxy. Protect `server.key`, node tokens, and panel token. Configure firewall rules so only intended ports are public. The agent token is shown only once at node creation.

## Not implemented yet
UDP, QUIC, KCP/FEC, WebSocket transports, full IP-layer TUN routing, SOCKS5/HTTP CONNECT, failover/load balancing, Telegram alerts, MFA, resource telemetry, and verified automatic updates are not part of this release.


## Publish on GitHub and one-line install

1. Create an empty GitHub repository (for example `OWNER/VPNSOPR`).
2. Change the module path in `go.mod` to `github.com/OWNER/VPNSOPR`.
3. Push the source to the `main` branch.
4. Create and push a version tag; GitHub Actions builds Linux AMD64 and ARM64 release archives:

```bash
git init
git add .
git commit -m "VPNSOPR v0.6.0"
git branch -M main
git remote add origin https://github.com/OWNER/VPNSOPR.git
git push -u origin main
git tag v0.5.0
git push origin v0.5.0
```

After the GitHub Release is published, install on Ubuntu/Debian VPS:

```bash
curl -fsSL https://raw.githubusercontent.com/OWNER/VPNSOPR/main/scripts/install.sh | sudo bash -s -- --repo OWNER/VPNSOPR
```

With a domain (create an A record pointing to the VPS first):

```bash
curl -fsSL https://raw.githubusercontent.com/OWNER/VPNSOPR/main/scripts/install.sh | sudo bash -s -- --repo OWNER/VPNSOPR --domain panel.example.com
```

The installer downloads a versioned GitHub Release asset, checks its SHA-256 file, installs a systemd service, and configures Caddy when Caddy is already installed. It does not install Caddy automatically.

### Panel address behavior

- Public VPS IP: `http://YOUR_VPS_IP` (HTTP; suitable only for initial testing or protected networks).
- Domain: `https://panel.example.com` when DNS points to the VPS and Caddy is installed and can obtain a public certificate.
- The Go panel itself remains bound to `127.0.0.1:7777`; Caddy is the public reverse proxy.
- The management API token is stored in `/etc/vpsopr/server.env` with restrictive file permissions.

**Security:** Do not use the panel over untrusted networks via plain HTTP. Prefer the HTTPS domain, a VPN, or SSH port forwarding. The agent listener uses a self-signed certificate generated by the installer; copy `server.crt` securely to each client and pass it with `-ca`. Do not expose the panel port 7777 directly.

## Additional administration features (v0.6.0)
- Maximum of 10 registered VPS nodes per gateway
- Rotate a node credential from the panel; old token is invalidated immediately
- Security response headers and no-store responses
- Systemd service and persistent configuration

After rotating a node token, update the client process on that VPS with the new token. The old agent will be rejected on reconnect.
